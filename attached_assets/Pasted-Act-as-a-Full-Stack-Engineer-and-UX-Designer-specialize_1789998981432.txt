Act as a Full-Stack Engineer and UX Designer specialized in Accessible Web Apps. Build a web prototype named "SIGNAL" - a tool designed to help deaf and hard-of-hearing candidates prepare communication support for job interviews.

Please strictly follow the P.R.O.M.T structure and guidelines below:

### P - PURPOSE
Build a high-contrast, accessible web prototype that solves the problem of deaf/hard-of-hearing job applicants missing communication accommodations during interviews. The entire user journey must be runnable in under 90 seconds without login or complex backends.

### R - ROLE & USER CONTEXT
Target User: Deaf/Hard-of-Hearing candidates (e.g., using Vietnamese Sign Language, captions, or written text). They interact via keyboard/mouse on a web browser. The app must NEVER ask for medical diagnosis or ask "Are you disabled?".

### O - OUTPUTS (6 Sequential Screens / Flow)
1. Screen 1 (Communication Profile): Multi-select options for communication preferences (VSL, Written text, Live captions, Interpreter, Questions in advance, Text-chat backup).
2. Screen 2 (Upload Invitation): Textarea to paste invitation email, upload placeholder, and a prominent "Sample Email" pre-fill button for fast demo.
3. Screen 3 (AI Interview Summary): Displays extracted details (Company, Role, Date, Time, Format, Platform, Duration) with editable inputs for candidate review.
4. Screen 4 (Communication Access Check): Displays gaps using clear status tags and color coding (Confirmed: Green, Needs Confirmation: Orange, Unknown: Gray, Not Available: Red). Include text labels alongside colors.
5. Screen 5 (Accommodation Request): AI-generated editable draft email requesting needed supports respectfully without declaring legal entitlements or revealing diagnosis. Include [Copy Text] and [Confirm Request] buttons.
6. Screen 6 (Employer Mock & Final Plan):
   - Top part: Mock HR Confirmation toggle list (simulate HR confirming/denying support).
   - Bottom part: "Final Interview Communication Plan" summarizing confirmed features and backup guidelines.

### M - MECHANICS & CORE FLOW
1. Step 1: User selects preferences on Screen 1 -> Click [Continue].
2. Step 2: User clicks "Use Sample Email" (or pastes email) -> Click [Analyze Interview].
3. Step 3: Extract/parse details (Company: ABC Company, Role: Marketing Intern, Date: 24 Sep, Time: 09:00, Format: Online, Platform: Zoom) -> User can edit -> Click [Continue].
4. Step 4: Run Accessibility Gap Engine logic:
   - Compare Profile preferences against Invitation details.
   - If support is explicitly mentioned -> 'confirmed'.
   - If selected preference is missing/unclear -> 'needs_confirmation' or 'unknown'.
   - Display statuses clearly. Click [Create Support Request].
5. Step 5: Generate draft request email -> Candidate edits/reviews -> Click [Confirm Request] (Shows notification "Request ready to send" - DO NOT claim "Email Sent").
6. Step 6: HR Mock Toggle updates states (e.g., check Live Captions, uncheck VSL Interpreter) -> Render final "Interview Communication Plan".

### P - POLISH & ACCESSIBILITY RULES
- Typography: High contrast, minimum font size 18px for body/inputs.
- Accessible Indicators: NEVER use color alone to convey status (always combine text label + icon + color).
- Keyboard Navigation: Fully navigable using Tab/Enter/Space keys.
- Tone & Aesthetic: Professional, calm, respectful. No pity-based or medical/clinical look. No flashy or long animations.

### T - TWEAKS, PLACEHOLDERS & OUT OF SCOPE
- No login, authentication, or complex database needed (use local state/React state).
- Fallback/Sample Data: Pre-fill sample invitation email and realistic data so the demo runs smoothly without real API dependency.
- Out of scope: DO NOT build sign language camera translators, candidate scoring/AI evaluation, facial analysis, real backend email sending, or HR user dashboards.
